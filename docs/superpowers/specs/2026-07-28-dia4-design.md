# dia4 — ambiente isolado por Pull Request

**Data:** 2026-07-28
**Status:** aprovado, aguardando plano de implementação

## Objetivo

Provar, num projeto mínimo, um fluxo profissional de PR: cada Pull Request ganha um
banco de dados isolado, tem suas migrations aplicadas, roda testes de integração
contra esse banco e publica uma URL navegável própria — que é destruída quando o PR fecha.

A demonstração central é esta: um PR cuja única mudança é **uma coluna nova no schema
Drizzle + a migration gerada** faz a coluna aparecer na tabela da URL daquele PR,
enquanto produção continua sem ela. Nenhum arquivo de front é tocado nesse PR.

Não é objetivo construir um produto. A aplicação é deliberadamente rasa para que o
pipeline seja a parte interessante.

## Arquitetura

Um único Cloudflare Worker serve tudo:

```
Worker "dia4"
├── dist/client/     React (build do Vite), servido como Workers Static Assets
└── worker/index.ts  Hono, atendendo /api/*
```

Mesma origem para front e API. Isso elimina CORS, elimina o problema de o front
precisar descobrir a URL da API do preview em que está rodando, e reduz o deploy a
um comando.

### Armadilha conhecida: roteamento de assets

Com `not_found_handling: "single-page-application"`, o Workers Assets responde
`index.html` para qualquer caminho sem arquivo correspondente — inclusive `/api/*`.
A configuração **precisa** de `run_worker_first` para as rotas de API:

```jsonc
// wrangler.jsonc
{
  "name": "dia4",
  "main": "worker/index.ts",
  "compatibility_date": "2026-07-28",
  "assets": {
    "directory": "./dist/client",
    "not_found_handling": "single-page-application",
    "run_worker_first": ["/api/*"]
  }
}
```

### Driver de banco

Workers não abrem sockets TCP, então o driver `pg` não funciona lá dentro. São dois
caminhos de acesso ao mesmo banco:

| Contexto | Driver |
|---|---|
| Worker (runtime) | `@neondatabase/serverless` + `drizzle-orm/neon-http` (HTTP) |
| `drizzle-kit` e seed (runner do CI, Node) | driver Postgres normal |

## Modelo de dados

```ts
// worker/db/schema.ts
export const students = pgTable("students", {
  id: serial("id").primaryKey(),
  name: text("name").notNull(),
  campus: text("campus").notNull(),
  course: text("course"),
  createdAt: timestamp("created_at").defaultNow().notNull(),
});
```

Migrations versionadas em `drizzle/`, geradas por `drizzle-kit generate` e aplicadas
por `drizzle-kit migrate` (que aplica apenas as pendentes).

## A API reporta o próprio schema

Esta é a decisão de design que faz a demo funcionar. O endpoint devolve as colunas
junto com as linhas:

```ts
app.get("/api/students", async (c) => {
  const columns = Object.keys(getTableColumns(students));
  const rows = await db.select().from(students);
  return c.json({ columns, rows });
});
```

`getTableColumns` lê a definição do Drizzle, não as linhas retornadas — portanto
funciona com a tabela vazia, o que `Object.keys(rows[0])` não faria.

O front renderiza os cabeçalhos a partir de `columns` e nunca precisa ser alterado
quando o schema muda:

```tsx
<thead><tr>{columns.map(c => <th key={c}>{c}</th>)}</tr></thead>
```

Escopo do front: somente leitura. Uma tabela, um `fetch`, estados de carregando e
erro. Sem formulários, sem edição, sem roteador.

## Testes

Vitest, executado no runner contra a branch Neon daquele PR.

1. **Seed** — `GET /api/students` devolve as linhas inseridas pelo seed.
2. **Coerência de schema** — as `columns` do endpoint são exatamente as colunas de
   `students` em `information_schema.columns`.

O segundo teste é o que dá sentido ao projeto: se alguém alterar `schema.ts` sem
gerar a migration correspondente, o schema declarado e o banco divergem e o PR
fica vermelho.

Playwright e testes end-to-end ficam fora do escopo desta entrega.

## Fluxo de CI

### `pull_request` — opened, synchronize, reopened

```
1.  checkout, setup node, npm ci
2.  typecheck
3.  neonctl branches create --name pr-${N} --parent production
4.  exporta DATABASE_URL da branch criada
5.  drizzle-kit migrate
6.  seed
7.  vitest        (integração, contra a branch do PR)
8.  vite build
9.  escreve secrets.json temporário com a DATABASE_URL da branch
10. wrangler versions upload --preview-alias pr-${N} --secrets-file secrets.json
11. comenta no PR a URL https://pr-${N}-dia4.<subdominio>.workers.dev
```

O passo 3 é idempotente: se a branch `pr-${N}` já existe (push subsequente no mesmo
PR), reutiliza em vez de falhar. O alias de preview é estável, então a URL comentada
no PR continua válida e passa a servir a versão mais nova.

O `secrets.json` vive apenas no runner e nunca é commitado.

**Atenção — secrets são do Worker, não da versão.** Uma versão anterior deste spec
afirmava o contrário, e a afirmação estava errada. Verificado em produção
(28/07/2026): o `versions upload --secrets-file` de um PR grava a `DATABASE_URL`
daquela branch Neon no secret store do **Worker**. Um `wrangler deploy` posterior
sem `--secrets-file` herda esse valor. Como o cleanup apaga a branch do PR ao
fechá-lo, produção passou a apontar para um banco inexistente e retornou 500.

Por isso o deploy de produção **precisa** passar `--secrets-file` com a
`DATABASE_URL` da branch padrão. Não é redundância: é o que impede um preview de
contaminar produção. O mesmo vale para qualquer `wrangler deploy` manual.

### `pull_request` — closed

```
1. neonctl branches delete pr-${N}
```

Roda mesmo se o PR foi fechado sem merge. Nenhum recurso da Cloudflare precisa de
limpeza — versões não promovidas simplesmente deixam de ser referenciadas.

### `push` na `main`

```
1. testes
2. drizzle-kit migrate  (branch production do Neon)
3. wrangler deploy
```

O deploy de produção fica num GitHub Environment chamado `production`, o que permite
exigir aprovação manual antes de liberar os secrets.

## Permissões e secrets

Workflow de PR precisa de `permissions: { contents: read, pull-requests: write }`
para comentar.

| Secret | Origem |
|---|---|
| `CLOUDFLARE_API_TOKEN` | Criado pelo usuário no dashboard (template "Edit Cloudflare Workers"). O login OAuth local do wrangler não serve no CI. |
| `CLOUDFLARE_ACCOUNT_ID` | `592d4fe686ebfceddb1d804472769efe` |
| `NEON_API_KEY` | `neonctl api-keys create`, redirecionado por pipe direto para `gh secret set` sem passar pelo terminal. |
| `NEON_PROJECT_ID` | Do projeto Neon dedicado, criado na org `org-restless-hill-40735252`. |

## Bootstrap

Ordem obrigatória, porque cada passo depende do anterior:

1. Criar projeto Neon dedicado ao `dia4` (os 4 projetos existentes ficam intocados).
2. Criar repo público `dia4` no GitHub.
3. Registrar os quatro secrets no repo.
4. **Um `wrangler deploy` inicial a partir da `main`.** O Worker precisa existir
   antes que `versions upload --preview-alias` tenha o que versionar.
5. Confirmar que a conta tem subdomínio `workers.dev` habilitado — sem ele não há
   URL de preview.

## Riscos

**Limite de branches do Neon.** O plano gratuito limita o número de branches por
projeto — o valor exato precisa ser confirmado no console antes do primeiro PR.
Vários PRs abertos ao mesmo tempo podem esbarrar nisso. O job de
cleanup no fechamento do PR é o que mantém o número baixo; se ele falhar, as branches
acumulam. Mitigação: o passo de criação usa "reutilize se existir", e branches órfãs
podem ser removidas manualmente com `neonctl branches list`.

**PRs vindos de forks não recebem secrets.** Com `pull_request`, o GitHub não expõe
secrets para forks. Num repo de um autor só isso não aparece, mas o pipeline
simplesmente falharia se alguém abrisse um PR de fork. Fora de escopo hoje; a
solução seria `pull_request_target`, que traz riscos próprios.

**Cold start do compute Neon.** Branches ociosas suspendem. A primeira requisição de
um preview antigo pode levar alguns segundos. É comportamento esperado, não bug.

**500 intermitente em `/api/students`, não diagnosticado (28/07/2026).** Numa
sequência de 5 requisições a produção, uma retornou 500; 45 requisições seguintes
retornaram 200 e o erro não reproduziu. A causa não foi identificada — a hipótese
não confirmada é cold start do compute Neon (projeto criado com
`autoscaling_limit_min_cu: 0.25` e suspensão automática por inatividade). Decidido
seguir para o CI: os testes de integração de cada PR exercitam o endpoint muito mais
do que testes manuais, e falhas passam a aparecer com log completo no Actions. Se o
sintoma voltar, comece por `wrangler tail --format json` durante carga concorrente.

## Fora de escopo

Autenticação, escrita pelo front (POST/PUT/DELETE), colunas definidas pelo usuário,
Playwright, diff de schema comentado no PR, Redis, filas, WebSockets.

A primeira evolução natural é adicionar escrita — e ela deve entrar como o primeiro
PR de verdade do projeto, exercitando o pipeline que este spec descreve.
